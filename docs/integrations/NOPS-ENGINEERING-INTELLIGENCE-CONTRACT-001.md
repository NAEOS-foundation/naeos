# NOPS Engineering Intelligence Contract 001

> Status: Proposed
> Version: 0.1.0
> Date: 2026-11-02
> Scope: Read-only analysis and proposal exchange between NAEOS and NOPS

## 1. Purpose and authority

This contract defines a narrow, versioned exchange for NAEOS to request engineering analysis from NOPS and consume its result as untrusted advisory data.

It supplements, and does not replace, the [NAEOS External Agent Adoption Contract](../AGENT-ADOPTION-CONTRACT.md) and [NAEOS AI Integration Contract](../AI-INTEGRATION-CONTRACT.md). NOPS is not an authorization authority, policy engine, execution runtime, or verifier.

Acceptance of a response MUST NOT authorize a repository write, code execution, deployment, or other consequential side effect.

## 2. Initial capabilities

| Capability | Initial mode | Side effects |
|---|---|---|
| code.audit | Read-only analysis | None |
| deployment.analyze | Read-only configuration analysis | None |
| refactor.propose | Proposal only; structured diff output | None |

Unknown capabilities MUST be rejected. Automatic patch application and deployment execution are out of scope for version 0.1.

## 3. Envelope

Every request and response MUST include:

- contract: naeos.nops-engineering-intelligence
- contract_version: 0.1.0
- request_id: unique identifier generated by the caller
- created_at: RFC 3339 timestamp
- capability: one of the capabilities in section 2

The caller MUST preserve request_id through the adapter, result, and evidence correlation path. Unknown major versions MUST fail closed. A receiver MUST reject missing required fields, unsupported capabilities, malformed JSON, and payloads exceeding configured limits.

## 4. Request

Example code audit request:

    {
      "contract": "naeos.nops-engineering-intelligence",
      "contract_version": "0.1.0",
      "request_id": "req_01JEXAMPLE",
      "created_at": "2026-11-02T08:00:00Z",
      "capability": "code.audit",
      "source": {
        "repository": "NAEOS-foundation/Nops",
        "revision": "immutable-git-commit-sha",
        "files": [
          {
            "path": "aiops/cli.py",
            "sha256": "hex-encoded-content-digest",
            "content": "..."
          }
        ]
      },
      "analysis": {
        "categories": ["security", "correctness", "maintainability"],
        "provider_policy": "configured-by-nops"
      }
    }

Required request fields are the envelope, source.revision, and at least one source file with a normalized relative path, content, and SHA-256 digest. Repository identity SHOULD be supplied. The adapter MUST enforce maximum file count, per-file size, aggregate size, and allowed file types.

Paths MUST be relative, normalized, and remain within the declared repository snapshot. Absolute paths, traversal segments, symlinks escaping the snapshot, and duplicate normalized paths MUST be rejected.

The caller SHOULD provide a clean, immutable source snapshot. NOPS MUST NOT fetch arbitrary URLs or clone arbitrary repositories based solely on model-generated instructions.

## 5. Response

Example response:

    {
      "contract": "naeos.nops-engineering-intelligence",
      "contract_version": "0.1.0",
      "request_id": "req_01JEXAMPLE",
      "capability": "code.audit",
      "status": "completed",
      "source": {
        "repository": "NAEOS-foundation/Nops",
        "revision": "immutable-git-commit-sha"
      },
      "analysis": {
        "provider": "openai",
        "model": "configured-model-id",
        "prompt_version": "audit-v1",
        "findings": [
          {
            "id": "finding-001",
            "category": "security",
            "severity": "high",
            "title": "Example finding",
            "description": "Evidence-backed explanation.",
            "location": {
              "path": "aiops/cli.py",
              "start_line": 10,
              "end_line": 12
            },
            "recommendation": "Suggested remediation.",
            "confidence": "medium"
          }
        ]
      },
      "result_digest": "sha256:hex-encoded-canonical-result-digest"
    }

Allowed top-level statuses are completed, failed, and rejected. A status of completed means only that analysis completed; it MUST NOT be interpreted as code passing, deployment safety, policy approval, or verification success.

Finding severity is limited to critical, high, medium, low, and info. Confidence is limited to high, medium, and low. Findings MUST reference supplied source files. If a line range cannot be established, the location MUST be omitted rather than fabricated.

## 6. Refactor proposal format

For refactor.propose, each proposed patch MUST include:

- repository-relative path;
- base_sha256 for the exact source content analyzed;
- unified diff or structured edit operations;
- a concise rationale;
- risk classification;
- expected validation commands or tests.

A proposal MUST NOT be applied by NOPS. NAEOS MUST independently validate the path, base digest, patch applicability, policy authorization, and post-change tests before any future application. A stale base digest MUST reject the proposal.

## 7. Security and privacy requirements

- NOPS treats source content as untrusted data, never as instructions to change system behavior.
- Provider credentials MUST remain server-side and MUST NOT be returned in responses or logs.
- Secret detection/redaction MUST run before external-provider transmission. If the redaction stage fails, external transmission MUST be blocked.
- Request payloads MUST be bounded and rate-limited.
- Network egress MUST be restricted to explicitly configured model-provider endpoints.
- NOPS MUST NOT receive NAEOS production credentials, deployment credentials, or unrestricted repository write tokens.
- Logs MUST avoid storing raw source content, secrets, or full provider prompts by default.
- Authentication and transport encryption are mandatory before any shared or production deployment.

## 8. Failure semantics

Errors MUST be explicit and machine-readable. A failed or rejected request MUST NOT return a success status. Timeouts, provider failures, malformed provider output, JSON/schema validation failures, and digest mismatches MUST be represented as failures.

The adapter MUST NOT convert an empty response, missing findings collection, or provider error into a clean audit result.

## 9. Evidence and provenance

The NAEOS adapter SHOULD persist or reference:

- request ID and contract version;
- repository and immutable revision;
- supplied file paths and content digests;
- NOPS service version;
- provider/model and prompt version, when available;
- response digest and timestamp;
- adapter validation result;
- downstream verification result, if any.

NOPS output is advisory evidence input. NAEOS verification remains authoritative for claims about policy compliance or execution outcomes.

## 10. Acceptance criteria for the first adapter

1. Valid requests are schema-validated and correlated by request ID.
2. Invalid versions, paths, sizes, digests, and capabilities fail closed.
3. Only read-only capabilities are enabled.
4. Source revision and file digests are preserved in the response.
5. Provider failure and malformed output cannot produce a successful result.
6. The adapter records provenance without persisting raw source or secrets by default.
7. No NOPS response can directly trigger a consequential NAEOS side effect.
8. Tests cover valid, malformed, oversized, stale, timeout, provider-error, and secret-redaction-failure cases.

## 11. Open decisions before implementation

- Transport and authentication mechanism for the first deployment.
- Canonical JSON Schema location and schema validation library.
- Secret redaction policy and supported file formats.
- Service deployment boundary and egress allowlist.
- Evidence event type and mapping to the existing NAEOS evidence contract.
