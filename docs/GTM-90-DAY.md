# NAEOS 90-Day GTM Execution Plan

Status: Execution baseline
Owner: NAEOS Business Development
Horizon: 90 days

## Objective

Prove a repeatable enterprise motion for NAEOS as **the control plane for AI-native software engineering**.

Primary outcome: convert technical interest into measurable design-partner usage and paid enterprise pilots.

## ICP

Primary ICP: engineering organizations with 50–2,000 engineers, GitHub-centric development, multiple repositories, established CI/CD, active AI coding-agent use, platform engineering/DevEx ownership, architecture/security controls, and a need for traceability or auditability.

Buying committee:
- Champion: VP/Director Engineering
- Technical champion: Platform Engineering / DevEx
- Security: CISO / AppSec
- Economic buyer: CTO / CIO
- Practitioner: Staff / Principal Engineer

Qualification:
1. Which AI coding agents are in use?
2. Can agents modify repositories or invoke CI/CD?
3. What actions are agents authorized to perform?
4. Where are architecture rules enforced?
5. Where are agent decisions recorded?
6. How are consequential actions revalidated?
7. How is evidence retained after an agent session?
8. What happens when an agent violates policy?
9. Which workflow is safe and valuable for a bounded pilot?
10. Who owns the engineering control boundary?

## Positioning

> **NAEOS is the control plane for AI-native software engineering.**

Supporting message:

> AI agents propose changes. NAEOS applies engineering policy and authorization before execution, then records evidence for verification.

Core architecture:

Specification → NEIR → Validation + Policy → Agent Context / Intent → Authorized Execution → Observation → Evidence → Independent Verification

NAEOS complements GitHub, CI/CD systems and AI coding agents; it is not positioned as a replacement for them.

## 90-day plan

### Days 1–15 — Positioning and readiness

- Finalize enterprise positioning.
- Publish design-partner offer.
- Prepare 3-minute control-plane demo.
- Prepare enterprise one-pager.
- Create CRM stages and account fields.
- Research 50 target accounts and 100+ named contacts.
- Establish baseline product metrics.

Exit criteria:
- 50 accounts researched.
- 100+ prospects identified.
- demo reproducible in under 5 minutes.
- design-partner offer ready.

### Days 16–30 — Discovery

- Run account-based outbound.
- Target 20 discovery meetings.
- Interview engineering, platform and security stakeholders.
- Identify one bounded workflow per qualified account.
- Record objections and buying criteria.

Exit criteria:
- 20 discovery meetings or documented attempts.
- 10 technical evaluations qualified.
- recurring pain statement documented.

### Days 31–45 — Design partners

- Sign 5 design partners.
- Limit each pilot to 1 team and 1–3 repositories.
- Establish baseline metrics.
- Integrate NAEOS with the selected workflow.
- Define policy and authorization boundaries.

### Days 46–60 — Evidence

Measure policy violations, blocked/allowed actions, manual interventions, review/rework, context preparation effort, verification results, and evidence generated.

Produce partner evidence packs without overstating results.

### Days 61–75 — Commercialization

- Offer paid pilot.
- Start security/procurement process.
- Package enterprise deployment model.
- Prepare SSO/RBAC/audit/security materials as applicable.
- Start partner conversations with GitHub, AI, cloud and SI ecosystems.

### Days 76–90 — Conversion

- Convert successful pilots to annual contracts.
- Publish 2 approved case studies where possible.
- Review ICP conversion data.
- Remove low-response segments.
- Select the next 50-account cohort.

## KPI dashboard

Acquisition: accounts researched/week, named contacts/week, personalized messages/week, response rate, meeting rate.

Qualification: discovery meetings/week, qualified evaluations, design-partner conversion, time from discovery to evaluation.

Product: active repositories, governed engineering workloads, policy decisions, authorized executions, blocked actions, verification results, evidence records.

Revenue: pilots, pilot-to-paid conversion, pipeline value, ACV, sales-cycle duration, expansion opportunities.

## North-star operating metric

**Governed Engineering Workloads**

A workload counts when a real engineering workflow crosses a NAEOS policy/authorization boundary and produces verifiable evidence.

## Outbound sequence

1. Problem: introduce the control-plane problem around agentic engineering.
2. Technical observation: share a concrete observation about agent authorization, policy or evidence.
3. Architecture: show Agent Intent → Policy Decision → Authorized Execution → Evidence.
4. Use case: offer a bounded workflow evaluation.
5. Design partner: invite the account to a 30–45 day founding design-partner program.

Do not use mass generic outreach. Personalize around the target company's engineering model and likely control boundary.

## Commercial hypothesis

Community: $0 — Apache-2.0 open source.

Team: hypothesis $25–50/engineer/month.

Business: hypothesis $75–125/engineer/month.

Enterprise: custom annual contract; initial ACV hypothesis $25k–$100k+.

Paid pilot: $10k–$20k for 6–8 weeks.

Pricing must be validated with design partners before being treated as final.

## Partnership lanes

1. GitHub — governance around agentic development.
2. AI providers — vendor-neutral agent governance.
3. Cloud providers — engineering-to-cloud control boundary.
4. Systems integrators — enterprise distribution and implementation.
5. Security/compliance partners — evidence and governance workflows.
6. Academic/community partners — research, benchmarks and adoption.

## Operating rule

Do not optimize for stars, traffic or feature count alone.

The 90-day GTM succeeds when NAEOS demonstrates:

**real engineering workload → governed execution → evidence → measurable outcome → paid adoption.**
