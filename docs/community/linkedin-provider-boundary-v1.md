# LinkedIn Provider Boundary v1

NAEOS uses LinkedIn as the first concrete external publisher adapter for the social-signal pipeline.

## Boundary

```
proposal
  -> policy decision
  -> human approval
  -> authorization-v1
  -> publisher dry-run
  -> external-publisher-v1
  -> last-controllable-boundary revalidation
  -> LinkedIn adapter
  -> LinkedIn Posts API
  -> provider receipt
  -> observation
```

The adapter is the first component allowed to perform an external provider HTTP request. It does not create authorization; it consumes authorization that has already been established and revalidates it immediately before the irreversible provider call.

## Credential boundary

The adapter receives a `LinkedInCredentialProvider` at runtime. Credentials are not stored in source, generated by the model, or passed through policy evaluation.

The credential provider must return a non-empty access token. An absent token fails closed and no provider request is made.

For organization posts, the LinkedIn application requires the `w_organization_social` permission and the authenticated member must have an eligible organization role.

## Request boundary

v1 supports text-only organization posts:

- endpoint: `POST https://api.linkedin.com/rest/posts`
- author: `urn:li:organization:<id>`
- visibility: `PUBLIC`
- lifecycle state: `PUBLISHED`
- `Linkedin-Version` is pinned in the adapter
- `X-Restli-Protocol-Version: 2.0.0` is required

The adapter rejects non-organization author URNs and empty commentary before any HTTP request.

## Receipt boundary

A successful LinkedIn post returns a provider identifier in the `x-restli-id` response header. NAEOS maps that identifier into `ExternalProviderReceipt.receiptId` and `externalId`.

Provider responses are observations. They do not grant authorization.

## Failure modes

The adapter fails closed for:

- invalid or missing authorization
- authorization contract mismatch
- missing execution/action bindings
- failed last-boundary authorization revalidation
- missing credentials
- invalid organization identity
- empty post content

HTTP failures are represented as rejected provider observations. Unknown provider outcomes remain `unknown` in the provider-neutral receipt contract.

## Operational rule

Do not place LinkedIn credentials in Git, PR bodies, logs, fixtures, or generated content. Production credentials belong in the deployment secret/runtime credential system.

The current adapter tests use an injected mock fetch and synthetic credentials. CI does not perform a live LinkedIn publication.
