# 2. NAEOS Partnership Thesis

NAEOS is building an open-source **AI Engineering Control Plane**.

The core architecture is:

```text
Specification
      ↓
     NEIR
      ↓
Validation / Policy
      ↓
   AI Context
      ↓
 AI Agent / Tools
      ↓
Execution / Generation
      ↓
Artifacts / Evidence
      ↓
Audit / Feedback
```

The key architectural principle is:

> **AI capability should not be confused with authorization.**

AI models can reason, generate plans, and propose actions.

Deterministic engineering controls should determine:

* what an agent is allowed to do
* which tools it can invoke
* which resources it can access
* which policies must pass
* which actions require approval
* what evidence must be generated
* how execution can be audited

Partners should therefore be evaluated according to how strongly they can help validate or extend this architecture.

# 4. Partner Priority Framework

Partners are classified using five dimensions.

| Dimension                     | Weight |
| ----------------------------- | -----: |

| Ecosystem reach               |    20% |

# 14. Partnership Types

Each partner should be approached with one primary partnership type.

### Type A — Technical Pilot

Build a small integration or reference implementation.

### Type B — Infrastructure Partner

Provide infrastructure, API, cloud, database, or observability resources.

### Type C — Developer Ecosystem

Expose NAEOS to developers through communities, events, or developer programs.

### Type D — Open-Source Collaboration

Contribute integrations, standards, documentation, or research.

### Type E — Startup Program

Explore credits, tools, technical support, and startup benefits when eligible.

### Type F — Research

Validate architecture, security assumptions, agent governance, or engineering methodology.

### Type G — Distribution

Co-marketing, technical content, events, or ecosystem exposure.

# 15. Outreach Rules

Every outreach should follow these principles:

1. **Lead with the technical problem.**
2. **Show the NAEOS architecture.**
3. **Propose a small pilot.**
4. **Avoid opening with a funding request.**
5. **Ask for a technical owner.**
6. **Mention startup benefits only after establishing technical relevance.**
7. **Never claim an existing partnership before it exists.**
8. **Never claim eligibility for credits without confirmation.**
9. **Use the partner's official startup/contact route.**
10. **Keep the first ask small enough to say yes to.**

* Working integration
* Public repository contribution
* Reference architecture
* Technical validation
* Deployment example
* Benchmark
* Case study
* Developer tutorial
* Community presentation
* Joint technical article
* Open-source contribution
* Startup program participation
* Infrastructure credits used for a demonstrable workload

# 24. Operating Principle

NAEOS should approach partnerships from the following position:

> **We are not asking partners to believe in NAEOS. We are asking them to help us test it.**

The strongest partnership is therefore not:

```text
Partner → Money → NAEOS
```

but:

```text
Partner Technology
        ↓
NAEOS Control Plane
        ↓
Real Engineering Workflow
        ↓
Validation
        ↓
Evidence
        ↓
Open-Source Integration
        ↓
Developer Adoption
```

This creates a compounding ecosystem:

```text
Technical Pilot
      ↓
Integration
      ↓
Evidence
      ↓
Case Study
      ↓
Developer Adoption
      ↓
New Partners
      ↓
More Integrations
      ↓
Stronger NAEOS
```
