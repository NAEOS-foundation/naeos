# NAEOS Category Authority Sprint — v2

**Status:** Execution draft  
**Window:** 2026-09-29 → 2026-10-28  
**Owner:** NAEOS Foundation  
**Objective:** Move NAEOS marketing from feature promotion toward category authority around AI Engineering.

## 1. Strategic thesis

> AI coding agents can write software. The engineering system around them must become explicit, verifiable, and governable.

NAEOS should be presented as an **AI Engineering Operating System / engineering control plane around AI coding workflows**, while preserving the repository's current verified product description: specification-driven engineering, declarative models, NEIR, validation, generation, AI context, governance, and reusable profiles/plugins.

Do not claim that NAEOS replaces coding agents. Do not claim customer adoption, enterprise production deployment, compliance certification, benchmark superiority, or partnerships unless repository evidence exists.

## 2. Category narrative

### Problem

AI-assisted development increases the speed at which code and repository state can change. Engineering intent, architecture, validation, context, policy, and evidence can become fragmented.

### New approach

Treat engineering intent as structured, machine-readable input and connect it to validation, generation, AI context, governance, and verification.

### NAEOS

NAEOS provides the open engineering layer for this workflow.

### Proof

Use only evidence that can be linked to the repository: architecture documents, CLI examples, tests, adapters, governance artifacts, profiles/plugins, and reproducible experiments.

## 5. Content production rule

Every major thesis must produce:

Thesis → Experiment → Evidence → GitHub artifact → Native social post → Community discussion → Learning

Do not manufacture content volume without technical evidence.

## 6. Conversion path

Content → Architecture/Experiment → GitHub → Quick Start → First successful run → Discussion/Issue → Contribution → Design-partner conversation

Primary CTA should be one of:

- Run the quick start
- Inspect the architecture
- Reproduce the experiment
- Challenge the thesis
- Contribute an issue/PR

Avoid generic “Learn more” CTAs when a concrete action exists.

## 7. KPI baseline

Track weekly:

- qualified visits to GitHub
- quick-start completion
- successful example runs
- GitHub referrals from content
- issues/discussions created
- first-time contributors
- profile/plugin activity
- repeat visitors
- qualified design-partner conversations

Follower count and impressions are secondary signals.

## 8. Execution gates

Before publishing any technical claim:

1. Locate the repository evidence.
2. Verify the implementation exists on the publication date.
3. Link the evidence.
4. Separate current capability from roadmap.
5. Avoid unsupported customer, benchmark, security, compliance, or production claims.

## 9. Definition of success

After 30 days, success means the audience can clearly answer:

1. What engineering problem is NAEOS addressing?
2. How is its architecture different from a coding assistant?
3. Where is the evidence?
4. How can I reproduce or inspect it?
5. How can I participate?

The campaign is successful only if content drives people toward those actions.
